# Threat model

Voting and submission abuse, as the event asked: for each attack, what the portal stops and what it does not.

## Sybil votes

**What is built:** the organizer chooses who may vote in the community vote, per event: signed-in accounts (one ballot per account), people on a voter list (one personal link per address, made by the organizer), and anyone holding the event's open link (one ballot per browser). Nobody can tell who holds the open link, so its ballots are counted apart: every count shows them in their own column, and they add to the result only if the organizer chose that before the first ballot came in (off by default, and the form says what the open link cannot stop before it is ticked). From the first ballot on the choice is fixed (409 `count_rule_fixed`), so it cannot be made after seeing the count. The other counting rules, who may vote and how many favourites each, can still change after the first ballot to fix a mistake, but only with a written reason: some ballots were cast under the old rules, so the change is audited with its reason and listed beside the count, on the public results page and the organizers' Voting tab. A person the portal can name has one ballot, not two: someone on the voter list who also has an account with that address, or who signs in and opens their link, keeps their picks on the ballot they started, and picks on the other answer 409 `already_voted` until the first is emptied. Opening a voting link only shows a page; entering takes a click, so link previews and mail scanners that fetch the URL never create a ballot. New open-link voters are limited per network address per hour: 8 unless the organizer sets another number (1 to 5000). A venue or office wifi puts everyone behind one address, so there the organizer raises it to the crowd's size, and the voting page says when a network ran out; the change is in the audit log. What then stands between one person and many ballots at such a venue is the one-ballot-per-browser rule, the flags on ballots from the same address and browser, setting ballots aside, and counting open-link ballots apart by default. Guessing a voting code is bounded too: each unknown code (opening a link page or entering with it) spends one of 30 tries per network address per 10 minutes, and once they are spent further unknown codes from that address wait (429). A real code spends no try and always goes through, even from an address whose tries are spent, so one person on a venue's wifi making up codes cannot lock out the voters behind it; the answers do tell a real code from a guess, which buys a guesser nothing, since each code is drawn from 144 to 192 random bits (about 142 to 190 bits of entropy, as three of the 64 symbols are written as one letter). Ballots that come from the same network address and browser are flagged to the organizer as suspected duplicates; while voting is open, the organizer can set one aside, only with a written reason, and undo it; both are audited. Publishing the results ends the vote: an open one closes at that moment, one not yet open is called off, and none can be set up afterwards (409 `results_published`), so nobody votes with the judged ranking in view; the publish row in the audit log says which. Once the window closes the count is public, and final: the window can no longer move (which would hide the count again and let more ballots in), no ballot can be set aside or restored, and no new links are made (409 `voting_closed`); nobody new enters through the open link (403, like a late ballot).

**What is not:** proof that an open-link voter is one person. Clearing cookies, another browser or another network makes a new voter, which is why those ballots are counted apart; the flags catch only the careless case, and people behind one shared address (an office, a venue's wifi) are flagged together, which is why the flag is a prompt for a human and never an automatic removal. Accounts are not email-verified (sign-up mails nothing, even with email on), so the account mode is only as strong as sign-up. The network address the entry limit and the flags use is the connection's own; an `X-Forwarded-For` header a client sends is ignored unless the operator says how many reverse proxies stand in front (`TRUST_PROXY_HOPS`), and then only the proxies' entries count (hand check B9 claims a new address on every attempt and is still limited). An organizer sees the live count and can set a flagged ballot aside, so an organizer could set aside ballots for a rival; each set-aside needs a written reason, is audited, and can be undone while voting is open, and once voting closes the log names what every ballot held, so the pattern can be checked afterwards, but nothing stops it in the moment.

## Ballot stuffing

**What is built:** each voter picks at most the organizer's number of favourites (3 by default), only among the event's submitted projects, and can change the picks while the window is open; the server checks all of it. The organizer can raise that number while voting is open but not lower it below a ballot already saved (409 `ballots_too_large`), so no counted ballot holds more picks than the rule allows. Nobody known can vote for their own team's project (422): not a signed-in person, whichever way they vote, and not a voter-list link whose address is a team member's account; their ballot says so instead of offering the button. The count applies the same rules when it is made: a vote for a project whose team the voter is on does not count. So no team change may move the count: joining the team of a project you voted for, leaving it, or being taken off it by its captain or an organizer is refused (409 `vote_would_change`) until the pick comes off the ballot (while voting is open) or an organizer voids the vote, which is audited. A vote on a copy the organizer merged counts for the copy it was merged into, once per voter (undoing the merge gives each copy its votes back). Saving a ballot is limited to 30 times a minute per voter (429 with `Retry-After`; the first refusal is audited). Every ballot change is audited with the picks before and after. Each ballot lists the projects in the voter's own seeded order, so no project gets the top spot on every ballot. While the window is open only organizers see the count, live on the Voting tab (the organizers' rule: results hidden from everyone but organizers), so voters and teams have no running total to chase. The audit log page and its CSV show that a ballot changed but not what it holds until voting closes (the rows are stored and hashed in full from the start), so the log never shows who picked what while picks can still change; and a webhook for a ballot change never carries the picks, since it goes out while voting is open. Nor does a ballot row's hash give them away, though its other fields and the hash before it are in the CSV and the webhook: with 40 projects and 3 picks there are only about 60,000 possible ballots to hash and compare, so each such row is hashed with its own 32 random bytes, shown in the CSV together with the picks once voting closes and never sent in a webhook (`DATA-MODEL.md`, the chain; `tests/audit-seal.test.ts` runs that search and finds nothing, and finds the picks when handed the salt). A ballot saved while an older version of the portal ran has no salt, so on a portal upgraded during an open vote those earlier ballots stay guessable from their hashes until voting closes; a new portal has none.

**What is not:** a CAPTCHA or any browser fingerprint beyond the address and the user agent; and a signed-out voter on the open link cannot be matched to a team, so the own-project rule and the one-ballot rule hold only for people it can name: someone signed in, or a voter-list address that belongs to an account. Open-link ballots are counted apart, so unless the organizer chose to count them they change no place (a signed-in person can still vote once more through the open link while signed out; from the same browser and network, that second ballot is flagged next to the first for the organizer). A merge can also join copies from two teams; the rule then follows the kept copy's team.

## Submission scraping

**What is built:** drafts are private, and the gallery and the API show only submitted projects. Comments need an account and are limited to 30 per 10 minutes per account.

**What is not:** a rate limit on reading. A client can read the public pages and API as fast as it likes; what it gets is what the event made public.

## Judge collusion

**What is built:** judges cannot read each other's scores (backend-enforced, tested, and checked by the organizers' suite); every score change is audited with before and after, and a webhook for one says who scored which project and when, never the values, nor anything to test guessed values against (the row's hash covers a salt the webhook never carries, as for ballots); the leniency model limits what one generous or harsh judge can do; the flat-judge rule catches a judge who scores everything the same; the judge ledger shows, for every judge, what leaving them out would move. A judge who should not be one (an open invitation link taken by the wrong account) is removed by an organizer with a reason: their access ends at once, and what they saved stays on record but out of the ranking, named as removed on the receipts, never shown to teams; a stale link cannot add a judge after judging closes or the results are published.

**What is not:** detection of coordinated collusion. Two judges trading favourable scores look like ordinary disagreement to the model; nothing flags that. The audit log keeps the evidence for an organizer to read.

**What is built, in pairwise mode:** answers are as private as scores: one judge's answers never appear in another judge's console, and only an organizer reads the ranking (both tested); every answer and every undo is audited, and a webhook for one carries only the judge and the track (the projects asked about would give the answer away, since binary insertion's next question follows the last answer), and its hash, salted like a score's, gives neither away; each project's receipt lists every comparison that entered the fit with the judge's name on it, so two judges answering alike can be read, not only suspected; and a flagged judge is kept or left out only by an audited organizer decision with a written reason.

**What is not, in pairwise mode:** collusion detection, again. The coin-flip flag rewards agreeing with the panel, so two judges who trade identical answers read as two judges who agree well; only their receipts side by side show it.

## One event's organizer reaching into another

**What is built:** accounts are shared by all the portal's events, and the two ways an organizer can act on someone's account without asking them follow one rule: an organizer reaches only people with no place (a role or a team seat) in an event that organizer does not run. Making someone a co-organizer by email is otherwise refused (403, audited), and the personal set-password links for imported people are made only for such people and checked again when a link is used, so a link dies if its person has joined another event since. An administrator reaches everyone, as they can send anyone a reset link anyway. Without the rule, one event's organizer could make another event's not-yet-claimed judge a co-organizer and then set that judge's password (`tests/organizers.test.ts`, `tests/import-claims.test.ts`).

**What is not:** consent inside an organizer's own reach. An organizer can still make an account with no other place a co-organizer without asking it, and an administrator can still bring anyone into any event; neither sets a password the person already has. An administrator also sees every event as its organizers do (the published role matrix gives ADMIN every column an organizer has, and each is a right to read), so an administrator is trusted with every event's scores and log by design; changing an event stays with its organizers, and an administrator's attempt to change or import onto an event they do not organize is refused and logged.

## Tactical pairwise answers

**What is built:** a judge cannot choose their questions. Which project sits on the left is a seeded coin per judge and question (the same sides every time that question is asked, the new project on the left about half the time), and the next question is whatever the replay of their own answers produces, so there is no hunting for a favourable pair. The two pulls, of the left side and of the project just opened, are measured from the event's own answers, and every strength is corrected by what was measured. In simulation the fit reads both pulls low (0.23 for a true side pull of 0.3, 0.13 for a true just-opened pull of 0.2, over 1,600 runs: JUDGING.md "The proof", check (c)), so part of each stays in. The balanced side coin keeps what stays of the side pull from favouring any one project; what stays of the just-opened pull depends on the order each judge opened their projects in, and how far that moves a place is not measured. "Too close to call" is half a win each way and places the project right below the one it tied with; it never says one project is better. A judge whose answers agree with the rest of the panel no better than coin flips, or who calls "too close to call" more than half the time, is flagged to the organizer: in the Monte Carlo that flags 50.8 % of judges answering at random and 7.3 % of honest ones, so a flag is a question for the organizer (keep the judge or leave them out, with a reason), never an automatic exclusion.

**What is not:** the strategic judge. One who answers honestly except for calling "too close to call" whenever their favourite would lose was flagged in 14 of 120 simulated panels, and the ties bought the favourite 0.26 places on average, at most 3 (`tests/pairwise-mc.test.ts`, check (e)): a tie earns half agreement and adds nothing to the flag's variance, so it is the cheapest answer to hide behind short of the tie rule. And the two pulls are one number per event: one judge's private habit of favouring a side is not measured per judge, only balanced by the seeded side coin, which puts the new project on the left in about half the questions (tested on the fixture's ids).

## Deadline gaming

**What is built:** the submission deadline and the voting window are enforced on the server: exclusive close times, refusals with 403, audited. A late duplicate submission is handled by the merge decision. Once any judge has saved a review or answered a pairwise question, the organizer can no longer move the submission deadline later or reopen submissions (409 `judging_started`), so teams cannot change what judges have already judged; moving it earlier stays possible. Password sign-in is limited to 10 attempts per email address from one network address per 15 minutes, so a stranger elsewhere cannot use up the owner's tries, and to 100 per email address per hour from all addresses together; sign-ups and sign-ins together are limited to 300 per network address per 10 minutes (the operator's `SIGN_IN_LIMIT_PER_ADDRESS`), since each one costs a password hash; a venue puts everyone behind one address, so the limit is sized for a crowd, and the per-email limits are what stop guessing. What is not stopped: someone with many addresses can still lock one account out of password sign-in for up to an hour by spending 100 wrong tries on it.

**What is not:** a grace period. The close time is exclusive by design: a submission or vote before it counts, one at or after it does not.

## Requests forged by another page

**What is built:** the session cookie is `HttpOnly` and `SameSite=Lax`, so a page on another site cannot make a visitor's browser send it with a write. A page on the same site but another origin (another app on the same host, a sibling subdomain) can, and the API reads a JSON body whatever type it declares, which lets such a page send a write that needs no CORS preflight. So an API write that the browser marks as coming from another origin (`Sec-Fetch-Site`, or `Origin` checked against the host for browsers that lack it) arrives without its cookies (`src/proxy.ts`): signed out, answered 401 like any anonymous call. The event import (`POST /api/imports`) is left out of the proxy so that it can take a 64 MB file, and applies the same rule itself: such a write is read with its cookies ignored. Requests without those browser headers (curl, scripts, the organizers' checker) and Bearer tokens pass as they are. The writes that set a cookie without needing one, signing in or up, setting a password with a personal link or a reset link (both sign the caller in) and entering a voting link, are refused outright from another origin (403 `cross_origin`), so such a page cannot sign a visitor in to an account its owner controls or enter voting in the visitor's name. The portal's own forms post to Next's server actions, which check the origin themselves, or to this API (Sign out), which the same rule covers.

**What is not:** a guard on sign-out: such a page can still end a visitor's session (a nuisance, not a takeover). Keep apps you do not trust off the portal's host and its parent domain.

## Uploaded files

**What is built:** only pictures are uploaded: a project's picture and up to 6 gallery images, by its team while submissions are open, through the same permission check and audit row as any edit; the refusal comes before the file is looked at or written. The portal reads the kind from the file's first bytes (PNG, JPEG or WebP; never the name or the declared type), so no SVG or HTML is decoded; stores not the file but the picture drawn again from its pixels (upright, at most 1600 pixels a side, as a WebP), so no metadata such as a phone photo's location comes through, whichever part of the file carried it; refuses anything over 8 MB, counting the body as it arrives, or over 50 megapixels, read from the header before the pixels are decoded; names each file with 128 random bits; and serves only names it made, as the image type, with `nosniff`. A refused upload leaves no file, and a replaced or cleared picture's file, or a gallery image's the team removes, is deleted unless another project shows it. An uploaded address can be sent back only by the project that holds it (as its picture, or in its gallery), so no team can show, and then delete, another team's file. An organizer can take any project's picture, or any one of its gallery images, down at any time, with a reason in the audit log.

**What is not:** a limit on how often a team replaces its picture or its gallery images (drawing one takes memory: the largest allowed that must also be turned took about 120 MB, and at most four are drawn at once, the size of Node's worker pool, so about 0.5 GB at worst; measured 2026-09-28); a cap below Next's own in front of the API, which holds up to 10 MB of any request body (server actions take up to 5 MB; the one larger body is an event file, up to 64 MB, which only `POST /api/imports` takes: that route is left out of the proxy, refuses anyone but an administrator before reading, and stops reading past 64 MB); and a scan of what an image shows.

## Filling the audit log

**What is built:** every refusal of a known person writes one audit row, so refusals are capped: past 60 in 10 minutes, one person (an account, or a voter holding a link) is answered 429 and nothing is written. A request with no valid session (401) never writes a row.

**What is not:** a cap across people. Many accounts, each under its own ceiling, still add rows; making accounts is itself limited (300 sign-ups and password sign-ins per network address in 10 minutes by default, the operator's `SIGN_IN_LIMIT_PER_ADDRESS`; see "Deadline gaming").

## The public default secret

**What is built:** `DOGFOOD_SEED_SECRET` derives the checker's sessions, salts the voters' address hashes and seals the signing key, and its default is published so that `docker compose up` works with no setup. With that default (or none) the portal starts only as the local demo: with demo mode off it refuses to start whatever `PUBLIC_URL` says (a portal behind a reverse proxy may leave it unset; judge's-eye reading 9), and a portal whose `PUBLIC_URL` is not this machine's own address (localhost, a name under `.localhost`, 127.x.x.x, ::1) refuses demo mode or not; each refusal comes before it opens the database and says what to set. With demo mode on it also refuses the checker's sessions there. Demo mode itself is refused on such an address whatever the secret, since its sign-in page makes anyone the demo organizer, an administrator, with one click; `PUBLIC_DEMO=true` (with an own secret) runs a public demo on purpose.

**What is not:** a check that an operator's own secret is long or random; and a portal in demo mode served to others while its `PUBLIC_URL` still names this machine or is unset, which the portal cannot tell apart from local use.

## Mail

**What is built:** email is off unless the operator sets `SMTP_URL`; then the portal mails each judge invitation that has an address, each listed voter's link, each claim link and each password reset link right after it is made, only to the address that action names (a reset only to the account's own). The permission check comes before anything is sent, and so does the outbox row: a message that cannot be recorded is not sent. The kept copy in the outbox has the link blanked, and the key itself is stored only as its hash, as before, so a copy of the database holds no working link. An address must be one plain address, by the same rule the screens use, and a subject cannot hold a line break, so nothing a person typed can add a recipient or a header. A send waits at most 10 s to connect or be greeted and 20 s of silence, once the server cannot be used at all, the rest of a batch fails at once, and a batch starts no new send after 20 s. The page that made the links waits at most 5 s for the mail server, then shows the links (their only copy) while the sends finish and write their outcome to the outbox. With `SMTP_URL` set, `PUBLIC_URL` must be too, or the portal refuses to start, since mailed links are built from it. `SMTP_URL` may hold the mail server's password; it lives in the environment, and no log line, error message or outbox row repeats it.

**What is not:** proof that a message arrived: "sent" means the mail server took it, and bounces go back to `MAIL_FROM`. When the connection breaks after the message was handed over, the outbox says "may have arrived" rather than "failed", and the screen advises asking before making a new link, since the new one replaces the link the person may already have. Mail travels as the server delivers it, encrypted in transit only where the servers agree to; a mailed link is as safe as the recipient's mailbox. Sending again later is not possible, by design: a new link is made instead.
